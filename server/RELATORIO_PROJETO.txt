1. VISÃO GERAL DO PROJETO
================================================================================

O plusTicket é uma plataforma completa de gestão de eventos que oferece:
- Cadastro e gerenciamento de eventos
- Venda de ingressos com múltiplos tipos (Pista, VIP, Camarote)
- Geração de QR Code único para cada ingresso
- Check-in em tempo real via leitura de QR Code
- Dashboard ao vivo com WebSockets mostrando entradas em tempo real
- Geração assíncrona de PDF de ingressos
- Envio automático de e-mails via fila de jobs
- Integração com Stripe para processamento de pagamentos

3. ARQUITETURA DO SISTEMA
================================================================================

3.1 PADRÃO ARQUITETURAL
-----------------------
O projeto segue uma arquitetura modular baseada em:
- Separação por Módulos/Domínios (Auth, Events, Tickets, Payments, CheckIn, Dashboard)
- Padrão MVC adaptado: Schema (validação) → Controller → Service
- Middleware pipeline para autenticação, validação e tratamento de erros
- Workers assíncronos via filas BullMQ
- Comunicação em tempo real via Socket.IO (namespace /dashboard)

3.2 DIAGRAMA DE FLUXO SIMPLIFICADO
-----------------------------------

  [Cliente] → [Express API] → [Controller] → [Service] → [Prisma] → [MariaDB]
                  ↓                              ↓
            [Middlewares]                   [BullMQ Queue]
          (Auth, Validate,                      ↓
           RoleGuard)                 [Workers assíncronos]
                                    (PDF, Email, Payment)
                  ↓
            [Socket.IO]
          (Real-time events)
          
3.3 FLUXO DE COMPRA DE INGRESSOS
----------------------------------

  1. Usuário seleciona ingressos → POST /api/tickets/purchase
  2. Sistema cria Order + Tickets (status: PENDING)
  3. Frontend solicita Payment Intent → POST /api/payments/create-intent
  4. Stripe processa pagamento no frontend
  5. Webhook Stripe confirma → POST /api/payments/webhook
  6. Sistema atualiza Order (CONFIRMED) e Tickets (PAID)
  7. Job de PDF é adicionado à fila → pdf-queue
  8. Worker gera PDF com QR Code
  9. Job de E-mail é adicionado → email-queue
  10. Worker envia e-mail com PDF anexado
  11. WebSocket emite 'ticket:sold' para o dashboard

3.4 FLUXO DE CHECK-IN EM TEMPO REAL
-------------------------------------

  1. Operador escaneia QR Code → POST /api/checkin
  2. Sistema valida: ticket existe? Pago? Não usado?
  3. Transação: Ticket → USED + Cria registro CheckIn
  4. Socket.IO emite 'checkin:new' para room event:{id}
  5. Socket.IO emite 'checkin:stats' com estatísticas atualizadas
  6. Dashboard atualiza em tempo real (sem refresh)

9. SISTEMA DE AUTENTICAÇÃO E AUTORIZAÇÃO
================================================================================

9.1 AUTENTICAÇÃO
-----------------

- Baseada em JWT (JSON Web Tokens)
- Access Token: expira em 7 dias (configurável)
- Refresh Token: expira em 30 dias (configurável)
- Senhas armazenadas com bcrypt (12 rounds de salt)

9.2 ROLES (PAPÉIS)
--------------------

Role          Permissões
----          ----------
ADMIN         Acesso total ao sistema
ORGANIZER     Criar/editar eventos, tipos de ingresso, check-in, dashboard
ATTENDEE      Comprar ingressos, ver meus ingressos

9.3 MIDDLEWARES DE SEGURANÇA
------------------------------

1. authMiddleware    → Valida JWT, busca usuário no banco, rejeita se inativo
2. optionalAuth      → Tenta autenticar mas não bloqueia se falhar
3. roleGuard(roles)  → Verifica se o role do usuário está na lista permitida
4. validate(schema)  → Valida dados de entrada com Zod
5. Helmet            → Headers de segurança HTTP
6. CORS              → Controle de origens permitidas

12. COMO EXECUTAR O PROJETO
================================================================================

12.1 PRÉ-REQUISITOS
---------------------

- Node.js 20+
- MariaDB 10+ ou MySQL 8+
- Redis 7+ (para filas BullMQ)

12.2 INSTALAÇÃO
----------------

  1. Clonar o repositório
  2. Instalar dependências:      npm install
  3. Copiar variáveis:           cp .env.example .env
  4. Configurar .env com suas credenciais de banco
  5. Criar o banco de dados:     CREATE DATABASE plusticket;
  6. Rodar migrations:           npm run db:migrate
  7. Gerar Prisma Client:        npm run db:generate
  8. Popular dados de teste:     npm run db:seed
  9. Iniciar em modo dev:        npm run dev

13. SEGURANÇA
================================================================================

13.1 MEDIDAS IMPLEMENTADAS
----------------------------

✅ Helmet - Headers de segurança HTTP (XSS, HSTS, etc.)
✅ CORS - Controle de origens permitidas
✅ JWT - Autenticação stateless
✅ bcrypt - Hash de senhas com salt (12 rounds)
✅ Zod - Validação de todas as entradas
✅ Prisma - Prevenção de SQL Injection por design
✅ Role-based access control (RBAC)
✅ Stripe webhook signature verification
✅ Rate limiting nas filas de e-mail (10/segundo)
✅ Expiração de pedidos (30 min sem pagamento → cancelado)
✅ Limite de ingressos por usuário (maxPerUser)

13.2 RECOMENDAÇÕES PARA PRODUÇÃO
-----------------------------------

⚠️  Configurar rate limiting na API (express-rate-limit)
⚠️  Usar HTTPS com certificado SSL
⚠️  Rotacionar JWT secrets periodicamente
⚠️  Configurar Redis com senha forte
⚠️  Usar connection pooling no MariaDB (PgBouncer equivalente)
⚠️  Implementar refresh token rotation
⚠️  Configurar WAF (Web Application Firewall)
⚠️  Ativar logging em serviço externo (DataDog, Sentry, etc.)

14. TRATAMENTO DE ERROS
================================================================================

O sistema possui um error handler centralizado que trata:

Tipo de Erro           Código HTTP  Resposta
-----------            -----------  --------
Prisma P2002           400          "Já existe um registro com este {campo}"
Prisma P2025           404          "Registro não encontrado"
ZodError               400          Lista detalhada de erros de validação
JWT TokenExpired       401          "Token expirado"
JWT Invalid            401          "Token inválido"
JSON Parse Failed      400          "JSON inválido no corpo da requisição"
Rota não encontrada    404          "Rota {METHOD} {URL} não encontrada"
Erro genérico          500          "Erro interno do servidor" (produção)
                                    Mensagem real (desenvolvimento)

Formato de resposta padrão:
{
  "success": true/false,
  "message": "Descrição da operação",
  "data": { ... } ou null,
  "errors": [ { "field": "...", "message": "..." } ] (opcional),
  "timestamp": "2026-08-12T19:46:00.000Z",
  "pagination": { "page": 1, "limit": 10, "total": 100, "totalPages": 10 } (opcional)
}

18. NOVAS REGRAS DE NEGÓCIO E MODELO DE MONETIZAÇÃO
================================================================================

18.1 MONETIZAÇÃO DA PLATAFORMA (RECEITA DO DESENVOLVEDOR)
-----------------------------------------------------------
Para garantir a sustentabilidade e lucratividade do sistema, foram estabelecidas
duas fontes principais de receita:

1. Taxa de Serviço / Conveniência (10%):
   - Cobrada diretamente do comprador no checkout sobre o valor total dos ingressos.
   - Discriminada no resumo do pedido e salva no banco (Order.serviceFee).
   - Exemplo: Ingresso R$ 100,00 + R$ 10,00 (10% Taxa de Serviço) = Total R$ 110,00.

2. Taxa de Saque por Antecipação (5%):
   - Retida pela plataforma quando um organizador solicita o resgate/saque
     antecipado dos fundos das vendas antes do término do evento.

18.2 RESTRIÇÕES DE CONTA DE ORGANIZADOR
---------------------------------------
1. Bloqueio de Compras:
   - Contas do tipo ORGANIZER não podem comprar ingressos (validado no backend com 403
     e desativado no frontend com aviso informativo na página do evento).
2. Ocultação da Aba "Meus Ingressos":
   - A aba "Meus Ingressos" é ocultada no menu (Navbar e BottomNav) para organizadores.
   - Rotas protegidas (/my-tickets) redirecionam organizadores diretamente ao Painel.

18.3 SISTEMA DE TRANSFERÊNCIA DE INGRESSOS POR E-MAIL (ANTI-GOLPE)
------------------------------------------------------------------
O recurso de transferência permite repassar um ingresso de forma 100% segura com
as seguintes diretrizes exatas:

- Destinatário Cadastrado: A transferência é permitida unicamente para e-mails que
  já possuem conta criada na plataforma.
- Confirmação em 30 Minutos: Ao enviar a transferência, o status fica PENDING com
  prazo de 30 minutos para aceite pelo destinatário. Caso expire sem aceite, o ingresso
  é automaticamente estornado para o remetente original.
- Limite de Transferências: Cada ingresso permite no máximo 2 transferências.
- Prazo Limite: Permitido até 2 horas antes do início do evento.
- Regeneração de QR Code (Segurança Anti-Golpe): Ao confirmar a transferência, o
  titular é alterado e um novo QR Code exclusivo é gerado. Qualquer PDF ou print antigo
  é instantaneamente invalidado na portaria.
